## A. オムツ使用個数のドロップダウン化

### A-1. UI

各品目行のステッパー `− 0 ＋` を `<select>` 1つに置き換える（＋−ボタンは削除）。

- 選択肢: `0 / 1 / 2 / 3 / 4 / 5 / 6以上`
- 「6以上」選択時のみ、右に数値入力欄（`type=number`・min=6・max=99・inputmode=numeric）を表示
- 既存値が6以上の日を開いたとき: selectは「6以上」・数値欄にその値を表示（値が見えなくなる事故の防止）
- 「残り少 ＋不足品」バッジは現状の位置・挙動のまま維持
- select は高さ44px以上（手袋タップ対応・既存ボタンと同基準）
- 0選択＝入力取り消し（該当行deleteの既存挙動を維持）

### A-2. データ

- **保存先・スキーマ変更なし**。`diaper_usage.count` に数値が入るのは従来通り
- 表示値⇔保存値の変換（select値と数値欄の合成、6未満を数値欄に入れた場合の丸め等）は
  純粋関数として `diaper-logic.js` に追加し、`node --test` でテストする
  - `usageToUi(count)` → `{sel: '0'..'5'|'6+', num: count|null}`
  - `uiToUsage(sel, num)` → count（不正値は安全側に丸める: 負値→0、'6+'でnum<6→6、num>99→99、非数→0）

## B. 「不足品」消失バグ修正（3点セット）

原因は調査済み・実ブラウザ再現済み（CURRENT_STATE参照）。要旨: `loadDateData()` のGET完了前に
autosave(800ms)が発火すると、新日付宛てに旧日付のメモリ内容（shortage等）が丸ごとupsertされ、
既存データを破壊する。GET往復が約0.9秒以上のとき発火。

### B-1. 画面側の根本修正（レースの排除）

- **ロード世代トークン方式**: `let loadGeneration = 0` を導入。`loadDateData()` 開始時に世代を進め、
  GET応答が返った時点で世代が変わっていたら**結果を破棄**（古い日付のデータで上書きしない）
- **ロード中の保存禁止**: `isLoading` フラグを導入。`scheduleAutoSave`/`saveCurrentData` は
  ロード中なら実行せず、ロード完了後に1回だけ再スケジュールする
- **保存対象日付の固定**: autosave発火時の `dateEl.value` 参照をやめ、スケジュール時点の日付を
  クロージャで束縛して渡す。発火時に表示日付と不一致なら保存しない
- ロード中はインジケータに「読み込み中…」を表示（現場が入力を待てる目印）

### B-2. 保存側の防御（destructive upsert の緩和）

- 保存前に取得する既存行（現状も `select('id')` している）を `select('*')` に変え、
  **画面がロードで受け取っていないカラムは既存値を維持**する。具体的には
  「この画面セッションで一度もロード成功していない日付への保存」を禁止する
  （ロード成功済み日付のセットを持ち、含まれない日付宛ての保存はスキップ＋console.warn）
- 全面的な部分更新API化はしない（GitHub Pages＋supabase-js直の構成では
  カラム単位の同時編集制御まで作り込むのは過剰。B-1で発火経路を塞いだ上の二重防御に留める）

### B-3. 履歴の保全（消えても戻せるように）

- 新規マイグレーション `migrations/2026-08-27_reports_history.sql`:
  - `reports_history` テーブル（reports全カラム＋`changed_at`＋`op`）
  - `reports` への UPDATE/DELETE 時に変更前の行を丸ごと記録するトリガー1本
- INSERTは記録しない（初回保存に「前」はない）。保持期間の自動削除は入れない（件数小・月数百行）
- 適用は本番DBへGetterが実施（非破壊・冪等: IF NOT EXISTS / CREATE OR REPLACE）
