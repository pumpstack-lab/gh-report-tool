# 現場ステッパーの「残り少」バッジ 設計書（2026-08-22・オーナー承認済み）

類似案件: `care-stack-absence/docs/superpowers/specs/2026-08-15-diaper-inventory-design.md`（オムツ在庫管理の本体設計）
— 差分: 本件はその現場入力側（ステッパー）に在庫の残り具合を出す追加機能。計算ロジック・DBスキーマは変更しない

## 目的

現場（世話人）が日報入力のついでに「このオムツは残りが少ない」と気づけるようにする。

**なぜ必要か（2026-08-22 ネイト指摘）**: このツールの在庫精度は、現場が毎日ステッパーを入力するかに完全依存している。入力を忘れると使用量が過少に集計され、残日数が**実際より長く出る＝在庫切れ方向に誤る**（安全側に倒れない）。現場に「自分の入力が在庫管理を動かしている」というフィードバックが一切ないと入力は続かない。バッジはその可視化を兼ねる。

## 確定済みの要件（オーナー回答 2026-08-22）

1. **表示は「少ない」だけ。残日数の数字は出さない**
   - 理由: 現場に発注権限はない。数字を出すと「どうすれば」と解釈を迫ることになる。現場が判断すべきは「報告すべきか」だけ
2. **発注サイクルは「随時」**（なくなりそうなら都度発注）
   - よって固定の発注日を守る必要がなく、**閾値7日/14日は変更しない**。現行値はリードタイム＋余裕として妥当と判断

## 既存設計との整合（重要）

本体設計書の line 87 は「オムツ行が未登録の利用者には何も表示しない（日報の見た目を変えない）」と定めている。本件はこの方針と矛盾しない:

- オムツ行が未登録の利用者 → 従来通り**何も表示しない**
- オムツ行があり、在庫が十分（ok）または実績不足（pending） → **何も表示しない**
- 在庫が少ない（red / yellow）→ そのときだけバッジが出る

つまり**平常時の日報の見た目は一切変わらない**。異常時にだけ情報が増える。

## 表示仕様

```
テープ式M（夜用）  🔴残り少   (−) 2 (＋)
尿とりパッド                 (−) 0 (＋)     ← ok/pendingは無表示
```

- 出すのは `red` と `yellow` のみ。`ok` と `pending` は無表示
- **文言は red / yellow とも「残り少」で共通**。色だけ分ける
  - 理由: 現場は発注しないので緊急度の段階を細かく伝える必要がない。文言を分けると「要注意と注意の違いは何か」を現場に覚えさせることになる
- 色は管理画面と同じ意味（赤=残7日以内・黄=残14日以内）
- 色のみに依存しない: バッジは常にテキスト「残り少」を伴う（色覚多様性対応・本体設計 line 79 と同方針）

## 計算ロジックの扱い（二重管理の明示的な受容）

`diaper-logic.js` を **gh-report-tool にもファイル単位で複製**する。

- **なぜコピーか**: 2つのツールは別リポジトリ・別デプロイ。gh-report-tool から care-stack-absence のファイルを `<script src>` で参照できない
- **なぜ一部移植でなくファイル丸ごとか**: 部分的に写すと「どこまで同じか」が追えなくなる。ファイル単位で同一なら `diff` 一発で検証でき、既存のNodeテスト14件をそのまま流用できる
- **正本**: `care-stack-absence/static/js/diaper-logic.js`
- **複製**: `gh-report-tool/diaper-logic.js`
- **運用ルール**: どちらかを変更したら必ず両方を更新し、`diff` で完全一致を確認する。両ファイルの先頭に相互参照コメントを置く

管理画面と現場で同じ `statusOf()` を使うため、**片方だけ判定が変わることがない**（数字がズレると現場の信用を失うため、ここは崩さない）。

## データ取得

`loadDiaperItemsForResidents()` に続けて、そのGHの品目分の在庫計算に必要な行を取得する:

- `diaper_events`（item_id, type, pieces, event_date）
- `diaper_usage`（item_id, usage_date, count）
- **⚠️訂正（2026-08-22 ネイト指摘・公式ドキュメントで検証済み）**: 当初「`.limit(10000)` を明示すれば1000行上限を回避できる」と書いていたが**これは誤り**。PostgRESTの `db-max-rows` は「A hard limit to the number of rows PostgREST will fetch」＝**サーバー側のハード上限**で、クライアントの `.limit()` では超えられない（変更はSupabaseダッシュボードの API Settings > Max rows）。管理画面側の同コメントも同じ誤りを含んでおり、要再検証
- **採用した対策**: 取得範囲そのものを増えない形にする。`diaper_usage` は
  「**最新の棚卸し日**」と「**直近14日**」のうち**古い方**を起点に取得する
  - `computeStock` は最新の棚卸し以降の全usageが必要（14日で切ると**在庫を過大評価**して在庫切れに気づけない側に倒れる。実測で158 vs 正110 のズレを確認）
  - `avgDaily` は直近14日のみ使用
  - 全期間取得と同一結果になることを4ケース（棚卸し30日前／5日前／棚卸しなし／棚卸し+納品）で実測検証済み
  - **棚卸しが1件もない品目は絞り込めない**（基準0枚から全usageを引く必要があるため）。定期的な棚卸しが行数抑制も兼ねる

対象は開いているGHの利用者分のみ（5〜7名・品目は十数件程度）なのでクライアント計算で足りる。

## エラー処理・エッジケース

- 取得に失敗した場合は**バッジを出さない**（日報入力そのものは従来通り動く）。在庫表示の失敗で日報が書けなくなるのは本末転倒
  - **⚠️実装上の注意（2026-08-22 ネイト指摘）**: supabase-jsは失敗時に**throwせず** `{data:null, error}` を返すため、**try/catchでは捕まらない**。`error` を明示的にチェックすること。
    特に **events だけ失敗すると `stock = 0 − usage合計` で大きなマイナスになり、在庫が十分にあっても全品目が赤バッジになる**（実測: 在庫-42・残-14日・判定red）。不正確な警告は現場の信用を失うため、取得に失敗したらバッジを一切出さない
- 過去日を開いている場合もバッジは**「今日時点の在庫」**を示す（残日数は現在の在庫と直近14日の平均から出る値であり、過去日の在庫を遡って再現するものではない）
- 在庫がマイナスの行も `red` として扱われる（本体設計 line 91 の「マイナスもそのまま表示」と整合）

## テスト方針

- 計算ロジックは既存のNodeテスト14件がカバー済み。複製したファイルに対して同じテストを流す
- **2ファイルが `diff` で完全一致することを検証**する
- 実ブラウザで red / yellow / ok / pending の4状態を描画確認（PC幅・スマホ幅）
- push前チェックリスト9項目完走（□9は本番確認まで）

## 報告経路（2026-08-22 ネイト指摘で追加）

バッジは**押せる**。タップするとその品目名が既存の【不足品】欄に1行追加され、押したバッジは「記入済み」になって無効化される。

**なぜ必要か**: 「残り少」と見えるだけでは現場は次に何をすべきか分からない。最悪なのは
**「バッジが出ている＝システムが知っている＝管理者にも見えているはず」という誤った安心感で報告が止まる**こと。
実際に管理画面には出ているので誤りではないが、**誰も発注しないまま在庫がゼロになる経路**が開通する。
オムツの在庫切れは利用者の尊厳に直結するため、ここは塞ぐ。

- 追加先は既存の `shortage-list`（管理者に届く正規の報告経路）。**新しい経路は作らない**
- 品名は自動で入るので手打ち不要（＝二度手間・表記ゆれの防止・ユーザーファースト設計原則）
- 同一品目の二重追加はガードする（連打・別日再訪でも増えない）

## スコープ外（YAGNI）

- 残日数の数値表示（オーナー却下）
- 現場からの発注機能・発注アラート通知
- 閾値の変更（随時発注のため現行値を維持）
- 閾値の設定画面化（値を変える理由が現時点で存在しない）
